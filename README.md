# Settlement Deduction Auditor

> You got ₹7,370 instead of ₹9,000. We tell you where every rupee of the
> difference went — and which parts you should be angry about.

An AI agent that audits every rupee a payment gateway deducted from a
merchant's settlement, and says which deductions were correct, which are
recoverable overcharges, and which put a tax credit at risk.

Razorpay Buildathon, Track 04 — AI Finance Controller.

---

## The gap this fills

| Layer | Question | Who solves it |
|---|---|---|
| 1 | Did the money arrive? | Razorpay — UTR, settlement_id |
| 2 | What was deducted? | Razorpay — fee, tax, adjustment columns |
| 3 | **Should it have been deducted?** | **This** |

A settlement report is a statement, not a verification. It proves the
arithmetic; nothing proves the *rate*. Those are different jobs and only one is
built — because no payment company builds the tool that bills itself. That is an
incentive problem, not a capability problem, which is why the gap does not close
when Razorpay hires better engineers.

**Fee validation is not a new discipline.** Optimus sells it to enterprises,
Cybiqon does it for marketplace sellers. What is missing is a version the 12
million merchants on Razorpay can use, gateway-side rather than
marketplace-side, agentic rather than a rules engine with a dashboard, and
merged with the TDS regime that changed on 1 April 2026.

Five independent 60-record batches, each generated with a known answer key:

```
 30 decoys             30 correctly dismissed
  0 false accusations
 65 agent decisions    65 correct
```

Reproduce it:

```bash
python audit.py --seed 11 --batch --db auditor.db
```

**What that number does and does not mean.** It is measured on synthetic data
generated by this repository, against errors this repository planted. It shows
the pipeline works end to end and that the agent never saw the answer key. It is
not a claim about accuracy on a real merchant's settlement file, which nobody
has tested because that data does not exist in a labelled form. Said plainly
because a judge will ask.

## How it works

```
synthetic generator (plants known errors, returns the answer key)
        │
        ▼
expected-value engine ──── pure Python, unit-tested against RBI circulars
        │                  "what SHOULD this have cost?"
        ▼
variance detector ──────── actual − expected, per line
        │                  emits SIGNALS: evidence + citation + rupee figure
        │
        ├─── 78% resolved here, deterministically. Never reaches the LLM.
        │
        ▼
Claude agent ───────────── decides WHAT KIND of gap each one is
        │                  5 read-only tools, structured output
        ▼
review ─────────────────── every figure it quotes must be one we computed
        ▼
guardrail gate ─────────── low confidence OR big money → human queue
        ▼
report ─────────────────── scorecard, findings, paste-ready disputes
```

### The core architectural rule

**The LLM never does arithmetic.**

Ask a model "is ₹610 the right fee on a ₹25,000 card payment?" and you get an
answer that is usually right and occasionally, silently, wrong. That destroys
the product, because the product *is* accuracy.

So the system is split. A calculator computes what the fee should have been —
deterministic, unit-tested, never wrong. The agent looks at the gap and decides
*what kind* of gap it is. A calculator can tell you the fee was ₹610 instead of
₹412; it cannot tell you whether that is a pricing error, a mislabelled
instrument, an unclaimed refund, or rounding. That second question is judgment,
and it is where the agent earns its place.

Enforced, not requested: every rupee figure the agent states is checked against
the evidence it was shown. A figure that was not in the input was derived or
invented, and either way the confidence is capped and the record is queued.

### This is agentic, not machine learning

No training, no dataset, no weights — deliberately. The rules are already
written down: UPI network MDR is 0% because the PSS Act says so, not because a
model inferred it from examples. Training a network to learn `fee = amount *
0.004` is training it to do the 7-times table. And a trained model cannot cite
a circular, which is the entire product.

Changing a rule is a one-line edit to `config/rate_card.json`.

## The ten rules

| # | Rule | Source |
|---|---|---|
| 1 | UPI network MDR = 0% | PSS Act s.10A, as amended 17 Aug 2026 |
| 2 | RuPay debit network MDR = 0% | same |
| 3 | Visa/MC debit ≤ ₹2,000 → cap 0.40% | RBI/2017-18/105 |
| 4 | Visa/MC debit > ₹2,000 → cap 0.90% | same |
| 5 | Credit card → contracted slab | merchant rate card |
| 6 | Amex / Diners / international → premium slab | merchant rate card |
| 7 | GST = 18% **of the fee**, never of transaction value | GST law |
| 8 | Refund → original fee is retained (expected, NOT an error) | industry standard |
| 9 | `method` says card but a UPI reference is present → mislabel | cross-field check |
| 10 | TDS code must match its date: 194O before 1 Apr 2026, code 1035 after | Income Tax Act 2025 |

Ten rules where the law is unambiguous. Judgment is left to the agent where it
is not — which explanation fits, whether a period boundary matters, whether an
unfamiliar adjustment can be accounted for at all.

**Rule 8 is the sleeper.** It prevents an entire class of false alarms, which
matters more for the accuracy number than catching one extra overcharge.

## Exception taxonomy

Categories are defined by **what the merchant must do**, not by what the error
looks like. Two records with identical arithmetic can land in different
categories, and that is correct.

| Code | Action | Recoverable |
|---|---|---|
| `CLEAN` | none | — |
| `ROUNDING` | auto-dismiss | no |
| `ZERO_MDR_VIOLATION` | **dispute** | yes |
| `INSTRUMENT_MISLABEL` | **dispute** | yes |
| `RATE_MISMATCH` | **dispute** | yes |
| `GST_MISMATCH` | fix books or dispute | partly |
| `REFUND_MDR_RETAINED` | book as cost | no — expected behaviour |
| `PERIOD_BOUNDARY` | reclassify, do not alarm | no |
| `TDS_CODE_MISMATCH` | **correct before filing** | tax credit at risk |
| `MISSING_FROM_SETTLEMENT` | **chase urgently** | yes |
| `UNEXPLAINED` | escalate to a human | unknown |

**Three of these mean "do nothing."** That is deliberate. A tool that flags
everything is one nobody opens twice. Knowing when *not* to alarm someone is
the differentiator.

## Two findings arithmetic cannot make

**A mislabelled instrument has a fee delta of exactly zero.** A UPI payment
tagged as a card is charged the correct *card* rate. Every number matches. It is
findable only through a cross-field check — a card payment carrying a UPI
reference. The agent then prices the difference:

> *"It was charged ₹357.42 at the Visa/Mastercard credit rate. Priced as UPI it
> would have cost ₹71.48. The difference is ₹285.94. Note that the fee is
> correct FOR A CARD — nothing in the arithmetic is wrong, only the instrument
> it was applied to."*

**A deduction that matches no rule must be refused, not explained.** The batch
contains one adjustment nothing accounts for. The correct answer is that it
cannot be accounted for:

> *"Please ask your gateway in writing for the narration behind
> adj_Ghn5NqY6OJ8apK before booking it — do not net it off as a processing cost
> until they explain it. I am not inferring a cause: nothing in the file
> supports one."*

Inventing a balancing entry to make the books look tidy is the exact audit
finding nobody wants.

## Guardrails

1. **The agent never writes to a ledger.** Not because it was told not to — it
   has five tools and all five are read-only. There is no write in its world.
   That survives a prompt injection hidden in a settlement file.
2. **Every classification carries** a reasoning trace, a confidence score, and
   the rule it relied on with that rule's source.
3. **Escalate, don't guess.** Confidence below threshold, or money above a rupee
   cap, or a correction applied during review → human queue, never auto-resolved.
4. **No invented balancing entries.** If something does not reconcile, it says so.
5. **Full audit log.** Every decision, with the evidence it saw, the tools it
   called, what review corrected, and what it cost. Timestamped and replayable.
6. **Nothing is ever marked reviewed by the system.** `human_reviewed` stays 0;
   a test asserts no code path sets it to 1.

A failed API call escalates. It never returns "clean" — silence is not
absolution.

## Data strategy — stated honestly

Razorpay test mode will not produce sixty realistic settlements containing
planted overcharges, and chasing that is a trap.

- **Schema fidelity** comes from Razorpay's Settlement Recon API field names and
  ID formats, mirrored exactly, so a real export would `INSERT` without
  translation.
- **Volume and planted errors** are generated synthetically in that shape.
- **Ground truth** is returned alongside the data and never touches it. The
  `Record` objects carry no label field of any kind — if they did, one careless
  line could turn the accuracy number into a lookup.

**Verified, not assumed.** `razorpay_check.py` creates a real order in test
mode and compares the response against what the generator produces:

```
created a real order: order_TSvPsArdnPRZ8I
  our id format matches  : True
  amount is integer paise: True  (162700)

order:
  confirmed real   amount, created_at, currency, id
  we do not model  amount_due, amount_paid, attempts, entity, notes,
                   offer_id, receipt, status
  we invented      none
```

We model a subset of the real fields, which is honest. We invent none, which is
the part that matters. Razorpay counts in integer paise and so do we.

Payment and settlement objects need a checkout completed in a browser, which
`razorpay_checkout.py` sets up — the tooling creates the order and hands you the
page, and you do the part that involves a card. Once a test payment exists,
re-running `razorpay_check.py` picks up those shapes too.

**The bank credits reconcile to the paise, and the batch still contains fourteen
problems.** Layer 1 passes. Layer 2 passes. Only Layer 3 fails. That is the
argument, and it is a test (`test_bank_credits_tie_out_to_the_paise`).

## Ledgerline — the platform

```bash
./run_platform.sh        # then open http://localhost:8000
```

Agentic financial services for Indian merchants. One agent is live; the rest of
the catalogue is declared and unbuilt, and says so.

**The thesis:** every agent here audits the same kind of gap — *something was
agreed or legislated, something else actually happened, and nobody checks
whether they match.* The settlement auditor does it for gateway fees. The shape
recurs across Indian merchant finance, which is why this is a platform rather
than a tool.

### This is not where sales happen

It is where they get **checked afterwards**. A merchant's money already flows
through their gateway; Ledgerline reads what the gateway *did* to it and says
which parts were wrong. Nobody types a sale into it.

That distinction is load-bearing and the app used to hide it — the first screen
was a form for entering sales, which made a settlement auditor look like a very
bad point-of-sale system. Where the data comes from is now an explicit choice:

| Source | What it is |
|---|---|
| **Razorpay account** | Read the merchant's real settlement reports over the API. This is the product. |
| **Built-in simulator** | Manufacture settlements locally so the auditor has something to work on. Scaffolding, labelled as such everywhere. |

Everything downstream is identical either way. The detector, the agent, the
gate, the dispute letters and the audit log neither know nor care which side a
settlement came from — which is exactly why the connector lives in its own
module rather than tangled into the pipeline.

**Live keys are refused.** Pulling real settlements needs an API secret, and
this prototype has no login: anyone who can reach the page can open any
business. So the connector accepts `rzp_test_` keys only, and the secret is
never written to disk — it is asked for at sync time and used once. Only the
public key id is stored.

The honest consequence: Razorpay test mode does not settle, so a test
connection finds zero settlements. The connector is real; there is nothing
behind it until it points at a live account.

| Page | What it does |
|---|---|
| Overview | Recoverable total, what is waiting on you, and a question box |
| Settlements | Every batch, and the findings in each |
| Ask | Put a question to the auditor about your own books |
| Agents | The shelf: what is live, what is planned, why each gap exists |
| Data source | Connect Razorpay, or use the simulator |
| Settings | Your rate card and the gateway simulator's behaviour |
| Simulator | *(demo only)* record sales and settle them |

### One design system, two artefacts

The web app and the standalone `report.html` are the same product and now look
like it. `merchant/views.py` splits the stylesheet in three:

| | What it holds | Used by |
|---|---|---|
| `TOKENS` | colour and base elements. No component hard-codes a colour. | both |
| `COMPONENTS` | cards, tables, pills, stats, money panels, findings | both |
| `SHELL` | the app frame — rail, top bar, page grid | the app only |

The report used to carry its own palette. It drifted the moment the app was
restyled, and left two views of the same data looking like different products.
A test asserts the exact shared constants appear in the generated report, so
they cannot drift again.

### The interface

Modelled on the visual language Indian merchants already use for money: a fixed
left rail, light surface, one blue accent, dense tables. Server-rendered, no
build step, no framework — the only JavaScript is a poll loop while an audit
runs.

Two things appear on **every** page, and both are load-bearing:

- **The business selector.** With no login, the current tenant is the only
  context a person has. Getting it wrong means acting on someone else's books.
- **The data-source indicator** in the top bar — `DEMO DATA · FAULT INJECTED`
  or `RAZORPAY · TEST MODE`. Borrowed from Razorpay's own `TEST` toggle, and
  for the same reason: nobody must ever be wrong about whether they are looking
  at real money or manufactured data.

Colour follows the **action**, not the exception code — the taxonomy is
organised by what the merchant must *do*, so the interface is too. Dispute is
red, fix-books amber, escalate violet, dismiss grey.

### Before there is anything to show

A screen of zeros is not neutral — it reads as broken, and it is the first
impression every new business gets. So the overview does not render empty
furniture. It shows a checklist of where you are, exactly one next action, and
a plain statement of what will appear here once a settlement has been audited.

The next action depends on the data source: a simulated business is pointed at
the simulator, a connected one at sync. Empty tables carry the same action
rather than a dead-end sentence.

### Watching an audit run

An agent call takes fifteen to twenty seconds a record, so the wait is made
informative rather than hidden behind a spinner.

The rules finish in milliseconds, and that half of the work is the interesting
half — so it is reported first and in full: *"1 settled by your rate card —
never sent to the model, 4 needed judgment"*, with the breakdown by code. Then
each verdict **streams onto the page as it is decided**, with the instrument,
the finding, the money at stake and the confidence. Underneath, a line naming
the record currently being looked at and what the evidence points at.

Twenty seconds of nothing followed by everything at once tells a watcher less
than the same information arriving as it happens.

### Ask the auditor

The classifier answers a question nobody asked — *"what kind of discrepancy is
this record?"* — which is right for a batch and wrong for an owner at 9pm
wondering why the payout was short. So there is a question box.

Same agent, same read-only tools, same ban on arithmetic — enforced harder,
because a free-text answer has none of the constraints a classification has.
**Every total the agent might be asked for is computed in Python and placed in
its briefing before the question**, under an instruction to quote and never
recompute. Afterwards the answer is checked for figures that were not in the
briefing; anything invented is shown to the merchant *flagged*, not hidden.

The briefing contains one business's settlements, findings and rate card, and
nothing else — there is a test asserting another tenant's figures cannot reach
it. The page states the scope in numbers rather than in a promise: *"4 audited
settlements, 12 records, 8 with findings, your rate card (9 instruments), and
nothing else."*

**Asking is asynchronous.** An answer takes ten to fifteen seconds, and a plain
form POST left the page blank for all of it, which reads as a hang. The question
now lands immediately and the answer arrives in place. Without JavaScript the
same route still redirects and renders — both paths go through one renderer, so
they cannot drift into different pages.

With nothing audited yet, the page shows what to do first instead of an input
box over an empty briefing: the agent answers from findings that exist, and a
box invites a question it can only refuse.

### A fault is not a wildcard

Each simulated fault touches specific rails, and the picker says which:

| Gateway behaviour | Affects | Finds |
|---|---|---|
| correct | nothing | a clean sheet |
| 0.90% network MDR on UPI/RuPay | UPI, RuPay debit | `ZERO_MDR_VIOLATION` |
| 0.40% above the contracted slab | cards, netbanking, wallet | `RATE_MISMATCH` |
| GST on sale value | every instrument | `GST_MISMATCH` |
| UPI recorded as a card | UPI | `INSTRUMENT_MISLABEL` |

This matters more than it looks. Set "card rate on UPI", take a Visa credit
payment, find nothing, and it looks like the auditor failed — it did not; the
fault does not apply to that rail. A test walks all 35 behaviour × instrument
combinations and asserts the picker's claims match what the auditor actually
finds, so the labels cannot drift from the truth.

And with the gateway set to **correct**, the auditor finds nothing at all. That
is the tool working. A system that reports problems when there are none is
worse than useless.

### Multi-tenant, because the rate card belongs to the business

"Charged above the contracted slab" is meaningless without a contract to compare
against — and a boutique doing ₹4 lakh a month and a chain doing ₹4 crore are
not on the same credit-card slab. That is what *negotiated* means. So each
business has its own rate card, its own gateway behaviour, its own books, and
its own guardrail thresholds.

RBI-capped and statutory rates are shown but **cannot be raised**. If a merchant
could enter "UPI network MDR: 0.90%", the auditor would stop reporting zero-MDR
violations — it would have been told they are contractual. The one rule a
merchant does not get to edit is the one Parliament wrote.

### The agent shelf

| Agent | Status | The question it answers |
|---|---|---|
| Settlement Deduction Auditor | **live** | Where did the difference between my sales and my payout go? |
| GST Input Credit Reconciler | planned | Which suppliers did not file, and what is it costing me? |
| TDS Credit Tracker | planned | Was tax withheld from me, and did it show up as my credit? |
| Payout Timing Auditor | planned | Is my money arriving on T+2, and what is the float worth? |
| Chargeback Defence Assembler | planned | Which disputes can I win, and what do I send? |
| Vendor Invoice Auditor | planned | Am I billed the rates my contract says? |

Exactly one has an implementation, and there is a test asserting that. A
convincing mock of a working GST reconciler is not a roadmap — it is a lie with
a progress bar. Planned agents render as unavailable and cannot be switched on.

Adding the second agent means writing a runner and flipping a status: the
registry, the per-business enablement, the run plumbing, the progress reporting
and the audit log are already generic. That work was done *before* agent two
rather than after.

### Three audiences, three surfaces

One interface used to hold a merchant's contract, the platform's agent
catalogue, and a switch that makes the gateway misbehave — three audiences on
one settings page with no boundary between them. They are now separated, and
two of the separations needed no login at all.

| Role | Sees | Can change |
|---|---|---|
| **Operator** | `/admin` — every business, every account, agent rollout | which agents are live |
| **Owner** | one business | the rate card, the thresholds, the data source, who else is a member |
| **Staff** | one business | nothing structural — reads findings, asks questions, runs audits |

**Owner is the role that matters**, and for a specific reason: every finding is
*"you were charged more than your contract says"*, so whoever can edit the
contract can silently switch findings off. Set UPI network MDR to 0.90% and the
auditor stops reporting zero-MDR violations — not because it broke, but because
it was told they are contractual. That is why staff cannot touch it.

**An operator is not automatically an owner.** Running the platform is not the
same as being entitled to read a contract you are not party to. `/admin` has no
route into a customer's books; an operator who needs one has to be added as a
member like anyone else — visibly, in that business's People list, where the
owner can see it and remove it.

**The fault switch moved to the simulator**, where it belongs. No real merchant
has a "make my gateway misbehave" control, and a customer-facing settings page
was the wrong place for it.

### Encryption at rest

Pulling a merchant's settlements needs their API secret, and a nightly sync has
nobody present to type one. So the secret is stored — **encrypted, with the key
held outside the database.** That last clause is the whole point: encrypting a
secret with a key kept beside it protects against nothing, it just makes the
theft two steps instead of one.

```bash
python -m merchant.vault                       # generates a key
export LEDGERLINE_SECRET_KEY=<the key>         # environment, never the repo
```

Fernet — AES-128-CBC with an HMAC-SHA256 tag. The authentication matters as
much as the secrecy: without it, someone with write access to the file could
swap the ciphertext for one of their own and the platform would send a
merchant's settlement requests wherever they pointed it.

**With no key configured, nothing is stored.** `None` means *cannot store
secrets*, never *store them in the clear* — there is deliberately no column that
could hold a plaintext secret, and a silent fallback is how a file ends up
holding credentials everyone believed were encrypted. Switching a business back
to the simulator deletes the stored secret, because a credential that outlives
the reason it existed is one nobody remembers to remove.

`LEDGERLINE_SECRET_KEY` accepts a comma-separated list for rotation: the first
key encrypts, all of them decrypt.

### Live keys: what actually gates them

Live Razorpay credentials now require **both** a configured vault and an
explicit `LEDGERLINE_ALLOW_LIVE_KEYS=1`. The opt-in alone would enable them on
an install with nowhere safe to put them, which is the exact failure the vault
exists to prevent.

Even then, the Data source page lists what is still missing rather than glossing
it — no TLS, so the session cookie has no Secure flag; no access log of who read
which settlement. Encryption at rest is one control, not a security posture, and
an install that looks safe and is not is worse than one that admits what it
lacks.

### The agent's terminal

Every settlement carries a live transcript of the agent working — timestamped,
first person, colour-coded. It streams while the audit runs and replays
afterwards:

```
16:09:26  >  Opening settlement run_1a02e342b75_765e48.
16:09:26  >  3 payments, Rs 23,482.00 sold, Rs 23,016.78 actually reached the bank.
16:09:26  >  Reading this merchant's contract: 9 instruments, GST 18% of the fee.
16:09:26  >  Checking every one of the 3 deductions against that contract myself.
             This part is arithmetic - I do not guess at it.
16:09:26  ✓  1 of 3 settled by the rate card alone. Those never reach a language model.
16:09:26  >  2 records the arithmetic cannot settle. Those need judgement.
16:09:26  >  pay_6I4R4XJknWwqiw - Visa/Mastercard credit, domestic, Rs 17,871.00.
16:09:26  >  The fee is Rs 357.42 and Rs 357.42 is exactly right for this instrument.
             Every number matches - which is why arithmetic alone would call this clean.
16:09:26  >  The engine flagged this under rule 9 - it looks like INSTRUMENT_MISLABEL.
16:09:40  ✓  INSTRUMENT_MISLABEL. Confidence 0.82. Rs 285.94 at stake, and my
             recommendation is to dispute. (891 tokens, 14s)
16:09:40  >  Every figure I just quoted traces back to the engine. I did not
             compute any of them.
16:09:51  >  Applying the guardrails: 2 I can close myself, 1 a person has to look at.
16:09:51  !  pay_6I4R4XJknWwqiw held - Rs 285.94, above the Rs 250.00 review threshold
16:09:51  ✓  2 dispute letters drafted. I wrote the argument; the figures underneath
             were assembled from the record, not by me.
16:09:51  >  Done. I have changed nothing - everything above is a proposal.
```

**Live and replayed use the same line builders.** The runner calls
`merchant/trace.py` while the audit is in flight; `trace.build()` calls the same
functions over stored data afterwards. If they were written separately they
would drift, and then a person would watch one story and read a different one
later. A test asserts the runner defines no narration of its own.

**Tool calls stream from inside the model call, not after it.** A single
classification takes fifteen to twenty seconds. Reporting its tool calls once
`classify()` returns leaves the screen still for the whole time the interesting
part is happening — which is what "it is not dynamic" means in practice. The
classifier takes an `on_event` callback that fires as each tool is invoked, so
the terminal moves while the model thinks.

**Any audited settlement can be replayed, for free.** The transcript is
scheduled client-side from stored offsets — no thread, no fake run, and no API
call. The pauses are the `latency_ms` the model actually took, so watching a
replay is watching the run rather than an animation of it. Speed control for
real time, 4× or 10×.

That exists for two reasons. It means the dynamic terminal can be **demonstrated
with no wifi and no credit** — the demo never depends on a working API key. And
it means UI work no longer burns credit: earlier, every screen was built against
a freshly-paid audit run purely to have something to look at, which was waste.

**It narrates nothing it did not do.** No tools called means no tool lines — a
transcript that invents activity is worse than one that is quiet. Tested against
the stored `tool_calls`.

It exists to make the split **visible**. "Arithmetic resolves most records, the
model is spent only on judgment" is the headline claim, and it is invisible in a
findings table where a record settled by a rule looks exactly like one a model
reasoned about.

### The access log

Guardrail 5 already logs what the **agent** decided. This logs what **people**
saw — the other half, and the half a finance product is eventually asked about.
*"Who in my company looked at the March settlement?"* now has an answer.

**A log recording only successes misses the interesting event.** Someone reading
their own settlement is routine; someone reaching for a business they are not a
member of is the thing you would actually want to know, and a success-only log
throws it away. So refusals are recorded with the same detail, and refusals are
what the operator's platform view shows.

Recorded: opening a settlement, reading a dispute letter, asking the agent about
the books, running an auditor, and every refusal. Not recorded: the agent
catalogue, the settings form, the overview — logging everything produces a log
nobody reads, and a log nobody reads answers no questions.

**Reading the log is itself logged.** A blind spot at the most sensitive page is
where someone would look first.

**Append-only by discipline.** SQLite cannot enforce it, so nothing in this
codebase writes an `UPDATE` or `DELETE` against the table and a test greps every
source file for both. A log that can be edited is not an audit log, it is a list.

Owners read their own business's log. Operators see refusals platform-wide and
nothing else: investigating an incident needs to know someone tried to reach a
business they are not in — it does not need, and is not entitled to, what that
business's settlements say.

One detail worth the trouble: a refusal records *"not reachable from this
business"* rather than *"belongs to another business"*, because the page
deliberately does not distinguish "someone else's" from "does not exist" — and
an audit log must not state a reason that might be false.

### Login throttling

Five failed attempts per address-and-email in fifteen minutes, twenty per
address, five signups an hour. The two obvious ways to build this are both
worse than the problem:

**Locking the account** is a denial-of-service primitive — anyone who knows a
merchant's email could lock them out of their own settlements, indefinitely,
for free. So nothing is ever locked: limits are windows that expire on their
own, and the tight one is keyed on *(address, email)* so an attacker exhausts
only their own budget. A test asserts the real owner can still sign in from
their own address while an attacker is hammering theirs.

**Counting only real accounts** turns the limiter into an oracle: "you are rate
limited" would mean "that email is registered", leaking exactly what the login
form is careful to hide. So attempts are counted whether or not the account
exists, failed signups count too, and the responses are identical.

`X-Forwarded-For` is only trusted when `LEDGERLINE_BEHIND_PROXY=1`. Trusting it
unconditionally would let anyone set it per request and have an unlimited
budget — a limiter that can be bypassed by typing is worse than none, because
it looks like one.

This is not a defence against a distributed attack; a thousand addresses each
get their own budget. That needs infrastructure this prototype does not have,
and pretending otherwise would be worse than the gap.

### Auth, and what it does not fix

scrypt with a per-user salt, constant-time comparison, sessions stored as
hashes so a copy of the database is not a set of live logins. Login failures
say nothing about which half was wrong, because distinguishing them tells
anyone who asks which email addresses are registered.

Auth was **necessary** for live Razorpay credentials, and encryption at rest was
the next control after it. Neither is sufficient on its own, which is why the
gate needs both plus a deliberate opt-in.

### The gateway is a visible simulator, not a hidden fixture

An auditor with nothing to catch demonstrates nothing. Rather than bury errors
in a fixture, the gateway has a **behaviour** you can see and change on screen.
Each option is something merchants actually report:

- charge correctly
- apply a 0.90% network MDR to UPI and RuPay, where it is mandated to zero
- charge 0.40% above the contracted slab
- compute GST on the sale value instead of on the fee
- record UPI payments as cards and price them at the card rate

`merchant/gateway.py` imports nothing from `engine/`, and there is a test
asserting it never will. The gateway does not know what the correct answer is
and the auditor does not know what the gateway was told to do — they meet only
through the settlement file, exactly as they would in reality.

### A live settlement has no answer key, and the page says so

Accuracy is never claimed from the platform. A settlement you type in has no
ground truth, so no percentage appears next to it; the measured number comes
from generated batches where the planted errors are known. There is a test
asserting the live page cannot show an accuracy figure — otherwise the
strongest claim in the project would quietly attach itself to an anecdote.

### It still works with no network

If the API key is missing or the credit has run out, the rate-card rules still
resolve most records and the page fills in — with a banner saying the agent was
skipped. A rules-only audit in front of judges beats a blank page.

## Running it

```bash
python3 -m venv .venv                # macOS has python3, not python
source .venv/bin/activate            # <- do this first, every session
pip install -r requirements.txt
export ANTHROPIC_API_KEY=sk-ant-...

./run_platform.sh                    # the merchant platform, port 8000

python audit.py --db auditor.db      # ...and persist the run
python report.py --out report.html   # dashboard, opens with no server
python -m pytest tests/ -q           # 404 tests
```

| Flag | Why |
|---|---|
| `--save run.json` / `--replay run.json` | record once, rehearse free, no API |
| `--batch` | Message Batches API, half price, minutes not seconds |
| `--effort` | thinking depth. Default `medium`, validated at 100% |
| `--model sonnet` | cheaper iteration; `opus` for anything you quote |
| `--preview` | print the prompts without calling the API |

**Cost:** ₹10 a validation run, ₹14 live, ₹0 to rehearse.

## Stack, and what is deliberately absent

Python, SQLite, the Anthropic SDK's tool-call loop, one generated HTML file.

**No** Postgres, Docker, auth, Redis, queues, cloud deployment, or React. Each
is a day that does not exist, and every one of them is a way for a demo to fail
in a room with bad wifi. The dashboard is a single self-contained file with no
build step and no network calls; rows expand using `<details>`, so it works with
JavaScript disabled.

### Deviations from the original plan, and why

- **Anthropic SDK tool runner, not the Claude Agent SDK.** The Agent SDK ships
  file-write, edit and bash tools. For an agent whose first guardrail is "never
  writes to a ledger", starting from a toolset that can write anywhere and
  switching parts off is the wrong direction. It also needs Node, which is one
  more moving part.
- **One HTML file, not React.** React needs Node and a package tree to draw four
  numbers and a table. The stated priority was fewest moving parts.
- **Two extra planted cases beyond the original twelve.** A measurement showed
  every record reaching the agent carried exactly *one* candidate explanation,
  so the agent was confirming the detector rather than judging. One record now
  fires two signals that disagree, and one fires a signal nothing explains.

## Layout

```
config/rate_card.json      the merchant's contract, with provenance per rate
engine/expected_value.py   what a fee SHOULD be. No LLM in this file.
engine/taxonomy.py         the eleven codes and what each means you must DO
engine/detector.py         actual vs expected; emits evidence, not verdicts
engine/gate.py             what the system may close by itself
engine/scoring.py          measurement against ground truth
engine/store.py            one SQLite file
agent/prompt.py            the system prompt. This file is the product.
agent/tools.py             five tools, all read-only
agent/classifier.py        the agent, plus the review that checks its figures
agent/batch_classifier.py  the same agent at half price
agent/dispute.py           agent writes the argument, Python writes the facts
generator/synthetic.py     the batch and the answer key
merchant/auth.py           accounts, sessions, roles. Attacked in tests, not assumed.
merchant/vault.py          encryption at rest; the key lives outside the database
merchant/ratelimit.py      login throttling that cannot be used to lock someone out
merchant/accesslog.py      who read which settlement, and who was refused
merchant/trace.py          the agent's run, replayed from the audit trail
merchant/sources.py        where settlements come from: Razorpay, or simulated
merchant/ask.py            the question box, and the briefing it answers from
merchant/views.py          the design system: rail, top bar, cards
merchant/catalog.py        the agent shelf. One live, five declared.
merchant/agents/           agent implementations; settlement.py is the live one
merchant/businesses.py     tenants, and the contract each one signed

razorpay_check.py          verifies our schema against the real API
tests/                     404 tests
```
